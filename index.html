01

Problem & motivation

Identity verification fails in two directions at once. Too strict and legitimate users cannot get through — usually the elderly, or anyone with a poor front camera. Too lenient and the whole system is worthless against a printed photo or a replayed video.

On top of that, biometric data is the most sensitive personal data there is. A pipeline that ships raw face images to a server and keeps them is a breach waiting to happen — which is why privacy constraints shaped the architecture before any model was chosen.

Core constraints

  1. C1

    Presentation attacks — printed photos, screen replay, deepfakes — must be rejected, not merely low-quality captures.

  2. C2

    Face matching has to survive differing capture conditions: lighting, angle, and the age gap against the ID photo.

  3. C3

    Biometric payloads are encrypted in transit, processed ephemerally, and never persisted as raw images.

  4. C4

    Verification is auditable — an institution must be able to see why a check passed or failed.

02

The solution

A Flutter app captures the ID document and a live selfie, runs quality checks on-device, and sends an encrypted payload to a Spring Boot verification service. A Python / TensorFlow microservice handles liveness and face-embedding comparison, returning a scored decision plus an audit record — never a stored image.

  1. 01

    Capture ID

    The user photographs their national ID. On-device checks test glare, blur, framing and the presence of all four corners before upload is even offered.

  2. 02

    Extract & validate

    The document region is cropped, OCR pulls the ID number and name, and MRZ/checksum validation catches a fabricated document.

  3. 03

    Liveness capture

    A short guided selfie sequence with randomized challenges — turn left, blink, tilt — is recorded and assessed for presentation-attack signals.

  4. 04

    Match & decide

    Embeddings from the selfie and the ID photo are compared. A composite of liveness, match and document scores resolves to PASS, REVIEW or FAIL.

Features, and the reasoning behind them

Challenge-response liveness

Randomized action prompts, recorded per attempt.

Why A pre-recorded video cannot answer a challenge it did not know was coming.

On-device quality gating

Blur, glare and framing are checked locally before any upload.

Why Most failed attempts die on the phone — saving bandwidth and sparing the user a round-trip for an unusable capture.

Embeddings, not images

Matching runs on normalized face embeddings against a calibrated threshold.

Why Robust to lighting and modest age differences, and no pixel-level image ever needs to persist.

Scored, explainable decisions

Each attempt stores its component scores and the reason for the outcome.

Why An institution has to justify a rejection, and thresholds can only be tuned if the components are visible.

Ephemeral biometric handling

Images travel encrypted, live in memory, and are deleted once the embedding is computed.

Why Minimising retention is the only real mitigation for a biometric breach.

03

System architecture

Two backend services with different responsibilities: Spring Boot owns identity, workflow state and audit; Python / TensorFlow owns inference and nothing else. Separating them lets the model be versioned, benchmarked and scaled independently of the application.

  1. 1

    Mobile client

    Flutter · camera plugin · on-device quality checks

    Guided capture flow, local blur and glare detection, encrypted upload, biometric unlock for the app itself.

  2. 2

    Verification service

    Spring Boot · JWT · workflow state machine

    Owns the attempt lifecycle, calls the inference service, records decisions and audit entries.

  3. 3

    Inference service

    Python · FastAPI · TensorFlow

    Stateless liveness and embedding endpoints. No database access, no user data retention.

  4. 4

    Data

    MS SQL Server

    Scores, hashes and decision metadata. Never images.

Relationships

  • verification_attempts is 1—1 with decision_records; an attempt without a decision is visibly incomplete rather than silently failed.
  • document_metadata links to the attempt and stores only a salted hash of the ID number — the raw number is never persisted.
  • thresholdVersion on every decision lets a past outcome be reinterpreted when thresholds change, without rewriting history.

Design rationale

  • Hashes instead of raw identifiers limit exposure if the database is compromised.
  • Component scores are stored separately from the composite, so model tuning never requires re-running verification.
05

Technical implementation

Frontend

  • Guided capture with a live overlay: document outline alignment, glare detection, and a stability check before the shutter fires.
  • The liveness flow issues randomized prompts and records the challenge seed used, so the server can verify the sequence was actually followed.
  • Payloads are encrypted on-device and uploaded with a per-attempt key; the app never writes captures to the photo gallery.

Backend

  • Spring Boot orchestrates the attempt state machine — CREATED → CAPTURED → INFERRING → DECIDED — with a timeout on each step.
  • Calls to inference carry a request-scoped id and no persistent identifiers, so inference logs cannot be joined back to a person.
  • Decision logic is a versioned, configuration-driven composite: weights and thresholds are data, not hardcoded branches.
  • Images live in memory for the duration of the attempt and are explicitly cleared afterwards; no temporary files on disk.

Deployment

  • The inference service is containerized separately, with its model version pinned and recorded in every decision.
  • Health checks distinguish service availability from model load state, so a deployed-but-unloaded model cannot silently pass traffic.
06

Security

No raw biometric storage

Images are processed in memory and discarded. Only scores, hashes and decision metadata persist.

Encrypted capture pipeline

TLS plus payload encryption with a per-attempt key; captures never touch the device gallery or local cache.

Challenge-seed verification

The server knows which prompts were issued and rejects a submission whose recorded sequence does not match.

Hashed identifiers

National ID numbers are stored salted-hashed, so a database leak does not expose identity numbers.

Rate limiting & attempt caps

Repeated failures trigger step-up review instead of unlimited retries — a security control and an anti-abuse control.

Full audit trail

Every access to a verification record is logged with actor, IP address and outcome.

07

AI implementation

Two specialized models behind one decision function. Both were selected for explainability and latency, and both are calibrated against a held-out set rather than tuned by intuition.

Liveness / presentation-attack detection

A CNN classifier over the captured frame sequence, trained to separate live capture from printed photos, screen replay and masks. It returns a continuous attack score, not a boolean.

Face embedding & matching

A face-recognition backbone produces normalized embeddings for the selfie and the ID photo; cosine similarity is compared against a calibrated threshold.

Document validation

OCR extraction combined with format, checksum and field-consistency rules — a heuristic layer that catches fabricated documents the vision models would happily accept.

Composite decision function

A weighted combination of liveness, match and document scores, mapped to PASS / REVIEW / FAIL. The REVIEW band exists deliberately: a borderline case goes to a human rather than being forced into a binary.

Threshold calibration

Thresholds come from ROC analysis on a held-out set, choosing for a target false-accept rate first and then optimizing false rejects — because in identity verification, the false accept is the expensive error.

08

User experience

First-time verification

  1. Consent and privacy explanation
  2. Capture ID with live alignment overlay
  3. Guided liveness sequence
  4. Wait for decision
  5. See outcome and next step

Retry after failure

  1. See the specific reason for failure
  2. Get targeted guidance — better light, remove glasses
  3. Retry within a limit

Key screens

Privacy consent

Plain-language explanation of what is captured, that images are not stored, and how long the decision record is kept.

ID capture

Full-screen camera with a document outline, live glare and blur warnings, and automatic capture on stability.

Liveness capture

One prompt at a time, large text, with a progress indicator through the challenge sequence.

Result

A clear pass or fail with an explanation and, on failure, exactly what to change next time.

UX decisions

Explain before you capture

Users who know why a step exists comply with it. Consent and instruction screens reduced abandonment noticeably.

Fail with instructions, not just a reason

“Poor lighting — move near a window and try again” is actionable. “Verification failed” is not.

Automatic shutter

Capturing only when the frame is stable removes the most common user error: a blurred photo taken too early.

Accessibility first

Large prompts, haptic and audio cues, and a slower pace option — verification is used by everyone, including people who are not comfortable with a camera.

Honest waiting state

Inference takes a few seconds; the UI shows the actual stage rather than an indeterminate spinner.

09

Challenges & solutions

Presentation attacks

Hard

Problem

A high-resolution printed photo initially passed the liveness check under good lighting.

Solution

Added randomized challenge-response with a server-verified seed, plus texture and screen-moiré signals in the classifier. Attack attempts now fail at the challenge stage regardless of image quality.

Match failures on legitimate users

Hard

Problem

ID photos are often years old and shot under different conditions, producing false rejects.

Solution

Lowered the hard-reject threshold and introduced a REVIEW band routed to human verification, tuning for false-accept rate first and then minimizing false rejects inside that constraint.

Biometric privacy exposure

Hard

Problem

Any pipeline that stores face images is a liability that grows with every user.

Solution

Redesigned for ephemeral processing: memory-only handling, no disk temp files, payload encryption, and a schema that stores scores and hashes only.

Inference latency on mobile networks

Medium

Problem

Uploading full-resolution captures made verification far too slow on 3G.

Solution

On-device quality gating rejects bad captures locally, uploads are downscaled to the resolution the model actually needs, and the inference service was quantized for faster CPU response.

Model and threshold drift

Medium

Problem

Changing a threshold silently reinterpreted the meaning of past decisions.

Solution

Every decision records its thresholdVersion and model version, so history stays interpretable and rollbacks are traceable.

10

Performance & quality

Optimizations

  • On-device quality checks eliminate most failed attempts before any network call.
  • Quantized models and batched embedding computation keep inference within a few seconds on CPU.
  • The stateless inference service scales horizontally with no session affinity.

Error handling

  • Inference timeouts fail the attempt into a retryable state rather than leaving it stuck in INFERRING.
  • Model load failures are surfaced by health checks and block traffic instead of returning default scores.
  • Client-side capture errors recover in place — the user retries the step, not the whole flow.

Testing

  • Model evaluation on a held-out set, reporting false-accept and false-reject rates at each candidate threshold.
  • A presentation-attack suite using printed photos, screen replay and video playback.
  • End-to-end tests across device classes and simulated low-bandwidth conditions.
  • Audit and retention tests asserting that no image bytes survive an attempt.
